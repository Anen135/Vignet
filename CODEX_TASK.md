# ЗАДАНИЕ ДЛЯ CODEX: Vignet — универсальная платформа Asset для ChatGPT

Ты работаешь **в существующем репозитории Vignet**, а не создаёшь отдельный новый проект. Сейчас основа — браузерное расширение Chromium (Manifest V3) с CSS-виньеткой и MCP Bridge, умеющим принимать команды ChatGPT. Требуется **постепенно превратить эту первую версию в платформу устанавливаемых независимых Asset-пакетов**: CSS, JavaScript, медиаресурсы, собственные действия и настройки, привязка к беседам. Полностью реализуй описанный ниже вертикальный функционал, не ограничиваясь проектированием, моками или одной демонстрацией.

## 0. Порядок работы и жёсткие ограничения

1. **Вначале изучи текущий репозиторий**: весь код, `package.json`, `manifest.json`, тесты, README, transport MCP, WebSocket, структуру хранения, команды запуска и реальную схему деплоя. Не предполагай, что он совпадает с первоначальным ZIP: после запуска рабочий MCP мог быть переведён со `stdio` на Streamable HTTP `/mcp` через Cloudflare Tunnel. Сохрани именно работающий вариант; не заменяй HTTP на `stdio` и не меняй публичный URL или формат подключения без необходимости.
2. Сохрани существующие MCP-инструменты **`set_vignette`** и **`get_vignette_status`**, их названия, параметры и смысл результатов. Старые вызовы обязаны продолжить работать. В частности: `enabled`, `color` (`#RRGGBB`), `opacity` (0..1), `innerRadius` (0..90). Старую виньетку реализуй как встроенный Asset `builtin.vignette` или адаптер к нему; сохрани и мигрируй ранее записанные `vignetteSettings`.
3. Не ломай существующее соединение `ChatGPT → MCP → Bridge → WebSocket → Extension`. Не смешивай транспорт и бизнес-логику. Не публикуй сервис без аутентификации. В локальном режиме используй loopback, а для внешнего — защищённый `wss://`/HTTPS и авторизацию.
4. **Только JavaScript, не TypeScript**; Node.js для сервера, JS + HTML + CSS для расширения. Не добавляй React, Tailwind, сложную IDE, маркетплейс, облачную синхронизацию или тяжёлый фреймворк без убедительной необходимости. Обычные Asset должны быть способны работать без React.
5. **GitHub/distribution by source**: расширение устанавливается распакованным, не требуется публикация в Chrome Web Store. Но ограничения и разрешения Chromium Manifest V3 всё равно обязательны. Никаких обходов политик безопасности через отключение CSP или выдачу удалённому коду привилегий расширения.
6. Работай по этапам, фиксируй результаты в `PLAN.md` с чекпойнтами и статусами; **после планирования непосредственно реализуй и протестируй**. Не останавливайся после создания каркаса. Не удаляй существующие функции ради упрощения.
7. Если не хватает доступа к реальному подключённому ChatGPT или браузеру, реализуй проверяемый локальный сценарий через mock MCP-клиент и тестовое расширение, явно отдели автоматически проверенное от ручного. Не заявляй об успешном E2E без настоящего E2E.

## 1. Суть архитектуры и терминология

**Asset** — самостоятельный устанавливаемый пакет, совмещающий любое количество CSS, JS, изображений, аудио и прочих медиаресурсов. Asset предоставляет публичный контракт действий и параметров. ChatGPT видит только назначение Asset, доступные действия, схемы аргументов и результат. Внутреннюю реализацию LLM знать не должна.

Примеры: `builtin.vignette`, `rain`, `dark-theme`, `music-player`, `calculator`. Asset может быть просто CSS-темой или полноценной программой с несколькими действиями. **Не называй отдельные CSS-файлы или изображения Asset** — это *ресурсы*, составляющие пакет.

Различай сущности:
- **AssetDefinition**: установленный пакет, версия, метаданные, код, ресурсы, декларация действий.
- **MediaResource**: бинарный файл с хешем и метаданными в общей библиотеке; на него могут ссылаться разные Asset.
- **AssetConfiguration**: сохранённые пользовательские настройки пакета.
- **AssetInstance**: конкретный запущенный экземпляр с ID, параметрами, состоянием, контекстом и жизненным циклом.
- **ExecutionContext**: привязка к браузерному профилю, вкладке и беседе (`global`, `chat`, позже расширяемые типы).

Логическая схема:

`ChatGPT → MCP tools → Bridge (auth, routing, ack) → Browser Extension → Asset Registry + Media Library + Context Manager + Asset Runtime`.

Внутри расширения отдели `Transport Client`, `Command Router`, `Asset Registry`, `Asset Package Installer`, `Media Store`, `Context Manager`, `Asset Runtime`, `Style Engine`, `Script Engine` и минимальный `Management UI`. Это границы модулей, не требование плодить десятки бессмысленных классов.

## 2. Публичный MCP-контракт (стабильный, универсальный)

Сохрани старые tools и добавь как минимум:

- `list_assets({query?, includeDisabled?})` — компактный список реально установленных Asset, их `id`, `name`, `description`, `version`, `enabled`, `actions` (имена + краткие назначения). В описании инструмента прямо объясни модели: при просьбе включить эффект/помощник/тему сначала обнаружить подходящий Asset.
- `describe_asset({assetId})` — подробное описание конкретного Asset, действий и JSON Schema аргументов, доступных scopes и требуемых разрешений. **Не передавай модели исходный JS/CSS и бинарные файлы по умолчанию**.
- `run_asset({assetId, action?, parameters?, scope?, target?, instanceId?})` — универсальный вызов; `action` по умолчанию `start`, если он определён. `scope` обычно `current_chat`, также `global`. Сервер/клиент валидирует параметры согласно декларации Asset, возвращает `instanceId`, реальное `status` и ошибки.
- `update_asset_instance({instanceId, parameters})` — обновление без повторного запуска там, где Asset это поддерживает.
- `stop_asset({instanceId?, assetId?, scope?, target?})` — остановка одного экземпляра или подходящих экземпляров по явным критериям.
- `list_asset_instances({scope?, target?})` — запущенные экземпляры и состояния.
- `get_contexts({})` — доступные контексты вкладок/чатов для явного выбора целевого контекста.
- `get_asset_status({assetId?, instanceId?})` — доступность расширения, статус установки/запуска и диагностические ошибки.

Для управления каталогом можно добавить `create_asset`, `update_asset`, `enable_asset`, `delete_asset` **только при безопасном подтверждении пользователем**. Генерация скрипта ChatGPT не должна автоматически означать разрешение на исполнение. Для бинарных файлов использовать установку ZIP через интерфейс расширения либо явный HTTPS-источник с проверкой размера, типа и хеша; **не гонять большие MP3/PNG через MCP-JSON**.

Все ошибки — машиночитаемые: `ASSET_NOT_FOUND`, `INVALID_PARAMETERS`, `EXTENSION_OFFLINE`, `TARGET_AMBIGUOUS`, `CONTEXT_UNAVAILABLE`, `PERMISSION_REQUIRED`, `INSTALL_CONFIRMATION_REQUIRED`, `SCRIPT_EXECUTION_FAILED`, `TIMEOUT`, `UNSUPPORTED_BROWSER_FEATURE` и т.д. Раздели transport ACK (`received`) и успешное исполнение (`applied`); `ok: true` только после подтверждённого применения. Используй `requestId`, идемпотентность при повторах, тайм-ауты и ограничение объёма сообщений.

**Не создавать новый MCP tool на каждый установленный Asset.** Работать с фиксированным набором инструментов, которые показывают актуальное содержимое каталога. Не рассчитывать на автоматическое обновление `tools/list` в уже открытой беседе. При установке Rain достаточно нового результата `list_assets` и `describe_asset`. Можно добавить `notifications/tools/list_changed` как дополнительную оптимизацию, но не как зависимость работы.

Обязательное условие: если открыто несколько браузеров/вкладок ChatGPT, **никогда не отправлять команду в случайный первый WebSocket или все вкладки без явного разрешения**. Разрешай однозначную цель либо возвращай `TARGET_AMBIGUOUS`, предлагая выбор. Не бери userId из произвольного текста, переданного LLM, как доказательство идентичности пользователя.

## 3. Формат автономного пакета `.vignet`

`*.vignet` — обыкновенный ZIP со строгой структурой. Пример:

```
rain.vignet
├── asset.json
├── scripts/
│   ├── main.js
│   └── particles.js
├── styles/
│   └── rain.css
└── media/
    ├── ambient.mp3
    ├── drop.webp
    └── icon.svg
```

Придумай и задокументируй `asset.json` JSON Schema (с версионированием `schemaVersion`), обязательные поля: `id`, `name`, `version` (SemVer), `description`, `entry` или массив `scripts`, `styles`, `media`, `actions`, `settingsSchema`, `permissions`, `execution`, `defaultScope`, `compatibility`. Добавь `author`/`license` как необязательные. `id` должен быть уникальным и стабильным (предпочтительно namespaced, например `community.rain`), имена/ID не должны позволять путь `../` или коллизии. Действия имеют понятные descriptions и стандартизированные JSON Schema аргументов/defaults; LLM получает их из `describe_asset`.

Пример контракта Rain (ориентир; доведи до своего валидного schema):

```json
{
  "schemaVersion": 1,
  "id": "community.rain",
  "name": "Rain",
  "version": "1.0.0",
  "description": "Дождь поверх интерфейса ChatGPT",
  "entry": "scripts/main.js",
  "styles": ["styles/rain.css"],
  "media": ["media/ambient.mp3", "media/drop.webp"],
  "defaultScope": "chat",
  "permissions": ["dom_overlay", "audio"],
  "actions": {
    "start": {
      "description": "Включить дождь на экране",
      "parameters": {
        "type": "object",
        "properties": {
          "intensity": {"type": "number", "minimum": 0, "maximum": 100, "default": 50},
          "sound": {"type": "boolean", "default": false}
        },
        "additionalProperties": false
      }
    },
    "stop": {"description": "Остановить дождь", "parameters": {"type": "object", "additionalProperties": false}}
  }
}
```

При импорте: валидируй ZIP, manifest и пути; ограничивай размер архива, суммарный распакованный объём, количество файлов и степень сжатия (защита от zip bomb); запрещай traversal, абсолютные пути, дубликаты, исполняемые нативные файлы и неподдерживаемые форматы; проверяй фактический MIME/сигнатуры там, где это возможно; показывай пользователю имя, автора, версию, действия, список разрешений и размер. Импорт — **не автоматический запуск**. Реализуй установку/обновление/удаление/экспорт пакета, конфликт версий, сохранение работающего состояния на ошибке обновления (rollback), минимальный `rain.vignet` как fixture.

Пакет не должен иметь зависимости от отдельных физических путей расширения, кроме публичного runtime API. Предоставь инструментарий/скрипт `npm run pack:asset` (или аналог) для разработчиков на GitHub, с проверкой схемы и формированием `.vignet`. Сохраняй исходный пакет или реконструируемые данные для повторного экспорта.

## 4. Media Library — глобальное локальное хранилище

Храни бинарные PNG, JPEG, SVG, WebP, ICO, MP3, WAV, OGG и другие выбранные поддерживаемые медиа **не в `chrome.storage.local`**, а в IndexedDB/OPFS с абстракцией `MediaStore`. Для настроек и небольших метаданных можно использовать `chrome.storage.local` или IndexedDB. Учти квоты, резервное место и атомарность обновления метаданных; предусмотри понятные ошибки `QUOTA_EXCEEDED`.

- Каждому ресурсу вычисляй SHA-256; ключ физического хранения — content hash.
- Один и тот же бинарный ресурс может использоваться несколькими пакетами без дублирования; веди ссылки/ownership и безопасную сборку мусора после удаления пакета.
- Поддержи таблицу `assetId + logicalPath → mediaHash`, `mime`, `size`, `integrity`.
- Разрешай media по логическим URL, например `vignet-media://...` **внутри runtime API**, а для отображения в DOM генерируй безопасные Blob URL (с отзывом через `URL.revokeObjectURL`) или другой реально работающий механизм; не предполагай, что браузер поймёт кастомную схему URL в CSS.
- CSS `url(...)` внутри Asset должен корректно разрешать относительные пути к ресурсам после установки, включая кавычки, несколько ссылок и повторное применение. Не использовать ненадёжную подстановку произвольного текста без нормального CSS-парсинга/тестов.
- SVG/HTML считать потенциально активным контентом. SVG для иконок использовать в безопасном контексте изображения; не вставлять непроверенный SVG в DOM как HTML. Учитывать CSP, cross-origin и ограничения `blob:`.
- Не передавать бинарные файлы через WebSocket Bridge при каждом запуске. Библиотека живёт локально в расширении, программа обращается по API ресурсов.

## 5. Asset Runtime, Style Engine и Script Engine

Обозначь стабильный контракт жизненного цикла:

```js
export async function mount(context, options) { /* return disposer or handle */ }
export async function update(context, options) { /* no-op or controlled restart */ }
export async function unmount(context) { /* cleanup */ }
```

Это **логический SDK-контракт**, а не требование наивно делать `import()` или `eval()` над текстом в content script. Реализуй допустимый для MV3 механизм загрузки и исполнения пользовательского JS. Исследуй `chrome.userScripts` (`USER_SCRIPT` по умолчанию) и учитывай availability/разрешение **Allow User Scripts** для современных Chromium. Динамический код без излишних полномочий. Сборку нескольких JS-модулей пакета в самодостаточный исполняемый бандл можно выполнять отдельным сборщиком при упаковке/установке; не заставляй импорт ES modules работать в user script world без проверки. Не применять `eval`, `new Function` или неограниченное внедрение удалённого JS в привилегированный service worker/extension page. Для небезопасного `MAIN` world требуй явное дополнительное разрешение, показывай риски и исключи его из обычного сценария Rain.

**Учитывай фундаментальное ограничение:** обычный скрипт, изменяющий DOM страницы, технически может читать текст беседы, даже когда запущен в изолированном JS-мире. Не называй isolated world полноценной песочницей конфиденциальности. Для максимально недоверенных Asset предложи более строгий sandboxed iframe и ограниченный message API, где возможна реализация; честно документируй уровень риска `dom_access`.

Runtime обязан:
- запускать CSS-only Asset без JS;
- применять и удалять CSS без перезагрузки;
- запускать несколько экземпляров, если `multipleInstances` разрешено;
- хранить `instanceId`, текущие параметры и runtime status;
- корректно обрабатывать `mount / update / unmount`;
- убирать созданные DOM-узлы, стили, обработчики событий, интервалы, observers, объекты URL и звуки при остановке;
- использовать `AbortController`, cleanup registry и/или явный disposer API, проверяя, что очистка действительно вызывается в том же исполняемом контексте;
- прекращать действия скрипта при переключении чата даже если `unmount` вернул ошибку — не заявлять строгую изоляцию, если её невозможно технически гарантировать;
- не блокировать интерфейс ChatGPT при сбоях, возвращать диагностическую ошибку.

Нельзя обещать, что произвольный уже выполненный JS возможно полностью откатить: глобальные monkey-patches/изменения состояния страницы могут требовать перезагрузку. Введи `requiresReloadOnStop`/`cleanupGuarantee`, явно показывай это при установке. Предпочитай управляемые API, не произвольные патчи.

### Эталонные Asset

1. **`builtin.vignette`** — прежняя виньетка с тем же поведением через новый механизм и legacy MCP adapter.
2. **`community.rain`** — независимый устанавливаемый Asset: рисует анимированные капли поверх ChatGPT, настройка `intensity` 0..100, опциональный звук из локального MP3, чистый `unmount`, отсутствие зависимости от MCP после запуска. Визуальный слой не перекрывает клики (`pointer-events: none`). При отсутствии user gesture звук может быть заблокирован политикой autoplay — это нормально, покажи пользователю понятную подсказку и fallback без звука.
3. **`example.theme`** — чистая CSS-тема, чтобы отдельно проверить Style Engine и настройку для текущего чата.

Тестовый Rain должен **физически поставляться отдельным `.vignet` архивом**, устанавливаемым через UI, а не быть захардкоженным в исходники ядра. Картинки/аудио используй с соответствующей лицензией или создай собственные простые тестовые ресурсы; не подтягивай случайные медиа по внешним URL.

## 6. Chat Context Manager — независимые настройки для каждого чата

Поддержи scopes `global`, `chat`, `temporary` (эфемерный пока chatId отсутствует); спроектируй расширяемость под `project`. Правила применения: глобальные Asset действуют в любой беседе, чатовые только при активном соответствующем контексте. Параметры per-chat могут переопределять глобальные через явно определённый и протестированный precedence rule.

ChatGPT — SPA: отслеживай обычную навигацию, `history.pushState/replaceState`, `popstate` и доступный `chrome.webNavigation.onHistoryStateUpdated`; избегай бесконечных MutationObserver и постоянного тяжёлого polling. Определи ID беседы по URL, если он там есть; НЕ читай содержимое сообщений для идентификации. Поддержи `/c/<id>`, известные формы URL проектов/чатов и новые беседы без ID; не делай вид, что ID всегда можно получить. Для временного чата используй ephemeral context, очищаемый при закрытии/уходе; при присвоении постоянного ID корректно мигрируй состояние.

При переходе A → B:
1. Вычисли контекст и нужный набор Asset/экземпляров.
2. Убери только то, что не должно работать в B; оставь глобальные.
3. Включи/восстанови Asset, привязанные к B.
4. Корректно отработай rapid navigation, reload, browser restart, несколько вкладок с разными чатами, несколько экземпляров одного Asset.
5. Не переноси настройку чата A в чат B и не отправляй команду случайной вкладке.

`current_chat` на MCP-уровне — это **маркер, разрешаемый расширением на конкретной вкладке**, а не гарантированное знание ChatGPT ID беседы. Если цель неоднозначна, запроси выбор через `get_contexts`, а не угадывай.

Состояния и конфигурации сохраняй локально, обеспечь миграции схемы хранения. Никакого глобального reset при обновлении пакета/расширения. Восстановление после перезапуска/перезагрузки должно быть предсказуемым и идемпотентным.

## 7. Bridge, авторизация, производительность и устойчивость

**Текущий рабочий Bridge сохраняется.** Добавь Router и обработку универсальных команд поверх существующего транспорта. При разработке учти существующий лимит WebSocket payload (в первой версии он мог быть 32 КБ), запросы > лимита должны явно отклоняться либо проходить через отдельный локальный механизм импорта. Большие файлы НЕ транслировать по MCP/WebSocket.

Переключение между Quick Tunnel, Named Tunnel и сервером на домашнем ПК не должно менять API Asset. Конфигурация endpoint вынесена из кода и не хранит секреты в Git. Сервис многоклиентный по модели: отдельная аутентифицированная сессия/устройство и маршрутизация в правильное расширение; авторизация на стороне MCP и расширения, запрет доступа одного пользователя к Asset другого. Короткоживущая привязка устройства (pairing) и отзыв токенов желательны, но не подменяй реальную безопасность `Origin` и общим токеном для всех пользователей. Если текущий сервер развёрнут только в single-user dev mode, сохрани его как **явно ограниченный** локальный режим и подготовь правильную multi-user схему для удалённого доступа; не объявляй insecure HTTP server готовым к публичному использованию.

Учти MV3 service worker lifecycle: его могут остановить при простое; не хранить единственный источник правды в переменных памяти. Реализуй переподключение, повторную синхронизацию installed/active assets и состояния клиентских вкладок, heartbeat только в рамках поддерживаемой браузером модели. Работающий Asset не должен исчезать при временном отключении MCP-туннеля: он запускается локально и продолжает работать, а удалённые вызовы корректно возвращают offline/error.

По возможности сохрани статическую структуру MCP `tools/list`, чтобы при установке нового пакета НЕ требовались повторная регистрация плагина, туннеля или MCP сервера.

## 8. UI расширения

Небольшой, быстрый, утилитарный UI на vanilla JS/CSS, без перегрузки:
- каталог установленных Asset (название, версия, описание, включён/выключен, источник, разрешения);
- импорт `.vignet` через file picker / drag&drop;
- экран проверки пакета и явного подтверждения установки/обновления и разрешений;
- список запущенных экземпляров с кнопками stop/restart и областью действия;
- простая форма настроек на основе `settingsSchema` / JSON Schema параметров, без отдельной логики под каждый Asset;
- вкладка или раздел общей Media Library (файлы, объём, связи, удаление только неиспользуемого);
- диагностический статус MCP Bridge/WebSocket/подключённого браузера;
- редактор исходного JS/CSS в MVP **не нужен**, достаточно импорта пакета и проверки метаданных.

Продумай, какое состояние хранится локально в расширении, а что знает Bridge. Доступность Bridge не должна блокировать управление установленными Asset через UI расширения.

## 10. Проверки, которые должны реально проходить

- Старый `set_vignette` по MCP включает красную виньетку с параметрами, `get_vignette_status` возвращает совместимый результат.
- Из UI устанавливается `rain.vignet`, затем **без изменения кода Bridge и без нового MCP tool** он появляется в `list_assets`; `describe_asset` возвращает действия и параметры.
- `run_asset({assetId:"community.rain",action:"start",parameters:{intensity:80,sound:false},scope:"current_chat"})` запускает эффект в выбранном чате и возвращает подтверждённый `instanceId`.
- `update_asset_instance` меняет интенсивность без утечки старых timers/listeners; `stop_asset` удаляет все капли, стили, объекты URL и подписки.
- Переключение из чата A в B останавливает Rain, а возврат в A восстанавливает конфигурацию/экземпляр; глобальный стиль при этом остаётся.
- Перезагрузка вкладки/браузера, отключение и повторное подключение Bridge не портят каталог, ресурсы и восстановление состояния.
- Два Asset используют одинаковый WebP/MP3 физически один раз, а удаление одного не ломает второй.
- Вредоносный ZIP с `../`, ZIP bomb, неверной схемой, поддельными разрешениями, неверным SHA-256, опасным SVG и запрещённым исполняемым содержимым отклоняется или безопасно обрабатывается без запуска.
- JS-пакет не исполняется без явно предоставленных разрешений пользователя; если `chrome.userScripts` недоступен, UI объясняет, как включить Allow User Scripts, и возвращает корректную ошибку.
- При нескольких вкладках команда с неопределённым `current_chat` не попадает случайно в чужой контекст.
- Никаких жёстко вписанных публичных endpoint и секретов, токенов или API keys в репозитории и исходниках расширения.
- Для каждого критичного модуля есть unit/integration tests; если браузерные E2E недоступны в среде, задокументируй точный ручной сценарий.

## 11. Этапы и checkpoints

**Stage 0 — Audit и план.** Прочитать существующий код, записать инфраструктуру и миграции. `PLAN.md`, risk list, baseline tests. Не переписывать приложение без аудита.

**Stage 1 — Core Model + Asset Spec.** Реестр, схемы, встроенный adapter для виньетки, storage migrations, unit tests. Старый MCP вызов работает.

**Stage 2 — Media Library + Installer.** Надёжный `.vignet` ZIP installer, SHA-256, dedup, IndexedDB/OPFS, pack/export, тесты атак и квот.

**Stage 3 — Runtime.** CSS и JS engine, mount/update/unmount, разрешения, поддержка встроенной виньетки и независимого Rain Asset.

**Stage 4 — Context Manager.** Определение чатов, scopes, восстановление и переключение A/B, вкладки, временные чаты.

**Stage 5 — Universal MCP.** `list_assets`, `describe_asset`, `run_asset`, `update_asset_instance`, `stop_asset`, статусы, target routing, ACK/errors; обратная совместимость.

**Stage 6 — UI, интеграция, release.** Минимальный каталог и настройка, smoke/E2E, документация установки, упаковки и развёртывания Bridge для GitHub.

После каждого Stage: обнови `PLAN.md` (`done / pending / blocked`), запусти релевантные тесты, устрани регрессии. Иди дальше без ожидания новых указаний, если нет объективной блокировки. Финальный отчёт должен содержать: что реализовано, изменённые файлы, запуск, какие тесты прошли, что осталось действительно непроверенным, точные ограничения.

## 12. Критерий завершения

Пользователь устанавливает Vignet Extension и существующий MCP-плагин ChatGPT. Затем скачивает **отдельный файл `rain.vignet`**, устанавливает его в расширение, и пишет модели: **«Включи сильный дождь в этом чате, без звука»**. Модель видит Rain через универсальные MCP инструменты, вызывает запуск с валидными параметрами; эффект появляется только в нужном чате, корректно выключается при переходе в другой чат, восстанавливается при возвращении; библиотека медиа работает локально. **При этом старый запрос «Сделай красную виньетку на 70%» работает без изменений.**

Не останавливай реализацию на красивом `PLAN.md`: задача — работающий, протестированный код и распространяемые через GitHub исходники.
